# Project Rules

## Package management
Always use `uv sync` to install dependencies — never `pip`, `pip3`, `uv pip install`, or `python -m pip`.

Dependencies are declared in `pyproject.toml`. To add a new package, add it there then run:

```bash
uv sync --dev   # install all deps including dev group
uv run pytest   # run tools through uv
uv run alembic ...
```

## Docstrings

Every public module, class, and function in `pipeline/` and `db/` must have a docstring. Follow these rules:

- **Module**: one line describing the module's purpose (placed before any imports).
- **Class**: describe what the class represents; list attributes in an `Attributes:` block when they are not obvious from the type annotations.
- **Function / method**: one-line summary, then (when non-trivial) an `Args:` block and a `Returns:` or `Raises:` block. Use Google-style formatting.
- Private helpers (names starting with `_`) get a single-line docstring only — no Args/Returns blocks needed.
- Keep docstrings factual: say what a thing *is* or *does*, not how it works internally. Never restate the function signature in prose.

## Test writing standards

These rules apply whenever writing or modifying `test_*.py` files. Follow them before writing any test code. They mirror the `/review-tests` criteria exactly — the hook will check for violations after every write.

### Structure & naming
- Test file mirrors the module under test (`pipeline/parser.py` → `tests/test_parser.py`).
- Test name describes behavior, not implementation: `test_refund_fails_when_charge_already_refunded` beats `test_refund_2`.
- One logical assertion per test. Multiple `assert` lines are fine if they describe the same outcome; testing two unrelated behaviors in one test is not.
- Follows AAA (Arrange / Act / Assert) with visual separation. The "act" line should be findable in under a second.
- No section-header comment blocks (`# ---…---`) — test names communicate intent on their own.

### Isolation & independence
- Tests pass in any order and in isolation.
- No shared mutable state between tests (module-level dicts, class attributes, global counters).
- No reliance on prior test side effects ("test A creates the user that test B queries").
- Each test cleans up after itself, or its fixture does — no leftover rows, files, or env vars.

### Database & SQLAlchemy
- Tests use a transactional fixture that rolls back per test rather than truncating tables.
- Session scoping is explicit: `function`-scoped session for isolation, `session`-scoped engine for speed.
- Nested transactions (`SAVEPOINT`) used when the code under test calls `commit()` — **never call `session.commit()` inside production code invoked from tests; use `session.flush()` instead** so the savepoint rollback still works.
- No test hits a real production-like database without an explicit marker (`@pytest.mark.integration`).
- Helper functions that create files or ORM objects belong in `conftest.py`, not inlined in the test module.
- Tests assert on database state (queried rows) when relevant, not just the return value — but don't over-assert on autogenerated fields like timestamps and IDs.
- Schema is built via Alembic migrations, not `Base.metadata.create_all()` — otherwise schema drift is invisible.

### Fixtures
- Fixtures live in `conftest.py` at the appropriate scope (don't put a service-specific fixture in the root conftest).
- Fixture scope matches usage: expensive setup (engine, app instance) is `session` or `module`; per-test data is `function`.
- Fixtures compose rather than duplicate (`authenticated_client` builds on `client` builds on `app`).
- No fixture does too much — if one creates a user, an org, three projects, and seeds permissions, suggest splitting it.

### Assertions
- Assert on content, not just counts. `len(results) == 2` is weak; also check `results[0].field == expected`.
- Assertions check behavior, not internal implementation details.
- Error cases use `pytest.raises` with `match=` to verify the exception message, not just the type.
- Floating point uses `pytest.approx`; datetime comparisons use a tolerance or freeze time (`freezegun` / `time-machine`).
- Cover every boundary condition named in the acceptance criteria (e.g. a "≤ 500 chars" rule needs a test at 499, 500, and 501).

### Mocking
- Mock at system boundaries only: filesystem (`builtins.open`, `pathlib.Path`), HTTP clients, external APIs. Never mock internal private helpers (`_parse`, `_build`, etc.).
- `unittest.mock.patch` targets the import location, not the source: patch `pipeline.parser.open`, not `builtins.open`.
- Never mock the SQLAlchemy session itself — use a real test DB.
- Always use `autospec=True` or `spec=` on mocks so signature changes break tests instead of passing silently.

### Coverage of cases
- Happy path covered.
- Each error branch covered (validation error, not-found, permission denied, conflict).
- Boundary conditions: empty list, single item, max length, off-by-one around spec-named thresholds.
- Cover both sides of every branch: the happy path and the rejection/error path.
- Cover all values named in the spec (e.g. all heading levels `h1`–`h4`, not just a subset).

### Pytest hygiene
- `@pytest.mark.parametrize` used when two or more tests differ by only one input/output value — do not copy-paste test bodies.
- Markers (`slow`, `integration`, `external`) applied so CI can shard or skip appropriately.
- No `print` statements; use `caplog` to assert on logs.
- Remove unused imports before finishing.

### Smells to avoid
- Test passes when you delete the function body (assertion is too weak or missing).
- Test name and test body disagree.
- Setup is longer than act + assert combined and isn't extracted to a fixture.
- `try/except` inside a test swallowing the failure.
- Hardcoded IDs, dates, or magic numbers without a named constant or factory.
